# M6 性能优化、情景标定与报告核心发现

日期：2026-10-28。本记录只覆盖本轮三项改动；数值均来自 `config/modules/*.json`，代码中没有写入文档示例常数。

## 1. 性能

| 200人单run | 本轮开始 | 本轮结束 |
|---|---|---|
| summary 模式 | 15.45 秒 | 4.6–4.9 秒 |
| full 模式（含逐抽明细） | 19.1 秒 | 7.6 秒 |

（更早的 622 秒问题已在上一轮通过 FK 索引解决。）

改动内容：
- planner 在初始化时把单阶段“下一 UP 所需抽数”分布预计算成只读 NumPy 查找表 `(pity, guaranteed) → pdf`，同一组曲线参数在进程内共享。截断卷积改用 `np.convolve`，玩家循环里不再重复做 DP，也不再 deepcopy。planner 版本升为 `planner_dp_v2`。
- RNG 新增 `draw_pair`：同一抽的 s_check/up_check 共享前缀哈希。
- CI 评估按 (库存签名, 场景, 日期) 做有界缓存；战斗代理按场景缓存摘要。
- 钱包只重建被扣款的批次。summary 模式在写入阶段提前跳过明细表。
- 新增依赖 `numpy>=1.26`。

**未达到 <2 秒的目标。** 剩下的耗时主要来自每一抽都要构造并写入完整的原子事件契约对象（抽取、钱包变动、库存变动和保底状态）。要再提速，就得改动事件契约或写入边界，这超出了“只改计算方式”的范围，本轮没有做。

逐位等价证据：
- summary 表摘要 `dbc270c31d58c3e1` 在全部优化前后保持不变。
- full 模式新旧对比：1,962 个决策中 0 个翻转，浮点最大差 1.1e-13。抽取、聚合、生命周期和面板各行全部一致。
- NumPy 表与逐抽参考 DP 的最大差小于 1e-15（`tests/test_m6_perf_calibration.py`）。

## 2. 情景标定（假设值，不是发现）

L2 战斗基准，`scenarios.json`：
- `product_power.growth_per_debut_step` 设为 0.19，B_ref_first 保持 125。
- 目标是：无支援的 0+0 中位寿命在 42–126 天；0+1 在 84–168 天，且出道当期和第 1 期 CI≥1；S_A 支援至少把寿命延长到 2 倍。
- 在格点中约 69% 的单位满足逐单位严格目标。DPS_09 的 0+0 出道 CI 为 0.99（来自 θ 跳变），属于已知例外。

L3 行为，`behavior.json`，标定种子 7101/7102，每次 200 人，参照为 Ref_Mechanism：

| 参数 | 值 |
|---|---|
| churn.base_hazard | 0.005 |
| churn.fatigue_sensitivity | 1.5 |
| fatigue.gap_weight | 2.0 |
| fatigue.failure_weight | 0.8 |
| utility.beta_hoarding | 2 |

- 目标：期末留存 0.70–0.85，并且流失集中在 P04–P08。
- 标定种子上的留存约为 0.76。只调高基础风险会让流失均匀地出现在早期，因此改由疲劳驱动。

参数变化后 `config_id` 为 `ba113477…6b8a`，旧结果不可与本轮结果混用。

## 3. v2 实验结果（outputs/benchmark_n200_v2，650 个搜索 run 和 3 个参照 run）

- Ref_Mechanism：期末留存 72.5%（核心层 82.2%），收入 189,078 元。Ref_HP 的留存低 30.5 个百分点，收入低 10.4%。Ref_Support 的留存高 5.5 个百分点。67% 的流失发生在 P04–P08，峰值在 P04。
- λ 从 0 到 2：核心层留存从 88.1% 降到 66.1%，收入单调下降。留存降幅最大的一步是 λ 1.5→2（−13.6 个百分点，约为其余各步的 4.8 倍），复核种子上也在同一区间。
- 更正：上一版把“配对收入差在 1.5–2 之间由正转负”写成了收入拐点。实际上那只是相对基准点的过零，不是收入峰值，报告已改为报告形状和最大步长。
- a 从 0.8 到 1.6：留存从 73.1% 升到 86.6%，收入上升。秩稳定性 rho：收入 0.90，留存 0.99。
- failure_weight 乘 0.75 / 1.25：留存分别 +8.5% / −6.2%，收入 +1.56% / −1.21%。budget_weight 的扰动对结果为零效应，其机制原因未单独验证。
